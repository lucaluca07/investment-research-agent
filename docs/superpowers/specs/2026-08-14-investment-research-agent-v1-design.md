# 个人投研 Agent V1 设计规格

日期：2026-08-14  
最近修订：2026-08-16（架构评审修订）
状态：架构评审问题已修订，等待书面规格复核
项目：`investment-research-agent`

## 1. 产品定义

本项目是一个本地运行、单用户使用的个人投研工作台。它不是选股器、自动交易系统或单纯的报告生成器，而是一套以证据为基础、以变化为驱动、具有时间一致性的研究系统。

系统维护以下研究闭环：

> 事实 → 变化 → 研究问题 → 可证伪论点 → 支持与反方证据 → 市场定价验证 → 催化剂与失效条件 → 版本历史

系统负责采集、计算、组织证据和提出研究建议；用户保留最终判断权。系统不直接输出交易指令，也不将复杂研究压缩为一个不透明的股票评分。

### 1.1 核心问题

系统必须能够回答：

1. 行业和公司最近发生了哪些重要变化？
2. 当前投资论点有哪些证据支持或反驳？
3. 股价处于什么位置，市场是否已经反映这些变化？
4. 接下来应观察什么，什么情况会使论点失效？

### 1.2 V1 研究范围

V1 聚焦 AI 服务器相关的高端 PCB 产业链，持续追踪：

- 胜宏科技
- 生益科技
- 中国巨石
- 金安国纪
- 中钨高新

系统允许按需研究任意 A 股公司，但临时研究对象不会自动进入持续追踪池。将标的加入追踪池必须经用户确认。

## 2. 关键设计原则

1. **确定性计算与 Agent 推理解耦。** 指标、财务计算、版本和状态变更由代码执行；Agent 负责解释、调查和提出建议。
2. **事实与结论可追溯。** 关键结论必须关联原始来源、数据日期、发布时间和生成过程。
3. **时间一致性。** 区分事实发生时间、对外发布时间、系统获取时间和研究使用时间，避免未来信息污染历史判断。
4. **变化优先。** 日常输出关注相对既有状态的重大变化；无重要变化时明确报告无变化。
5. **反证优先。** 每个核心论点同时维护支持证据、反方证据和明确失效条件。
6. **渐进式数据策略。** V1 使用公开数据跑通，但所有数据源通过 Provider 接口隔离，后续可替换付费服务。
7. **行业能力模块化。** PCB、煤炭、有色等通过 Research Pack 扩展，不修改通用研究内核。
8. **Agent 能力保持轻量。** V1 直接使用 pi，不建设通用 Agent Runtime；投研状态和确定性工作流保留在业务系统中，避免被 Agent 会话替代。

## 3. 总体架构

### 3.1 数据源层

数据源按领域拆分：

- 行情、基准指数与 ETF
- 公司行动与交易日历
- 公司公告与定期报告
- 财务、分部和运营数据
- 宏观、利率、汇率和商品价格
- 行业资料、政策、新闻和调研资料

每类数据通过统一 Provider 契约接入。业务逻辑只能依赖标准化数据结构，不能直接依赖某个公开网站或供应商字段。

### 3.2 存储层

- 原始文件与响应：按来源和获取批次归档，不可静默覆盖。
- Parquet：保存未复权 OHLCV、复权因子、交易状态及其他时序数据。
- DuckDB：保存实体、事实、指标元数据、事件、证据、论点、催化剂、研究运行和版本关系。
- 派生缓存：保存可重建指标，并记录公式版本和输入数据版本。

日线和周线为 V1 的标准行情粒度。分钟线和 Tick 数据不在 V1 范围。

### 3.3 确定性分析层

该层负责：

- 财务与分部变化计算
- 价格位置与技术指标
- 相对强弱与横截面对比
- 估值历史分位
- 市场与宏观状态
- 异常变化检测
- 历史评估与可重放计算

Agent 不自行计算这些指标，只读取带口径、日期和版本的结果。

### 3.4 通用研究内核

该层负责：

- 文档采集、解析和引用定位
- 事实抽取与去重
- 变化检测和事件归并
- 检索与证据关联
- 宏观 → 行业 → 公司传导关系
- 论点、反证、催化剂和版本管理
- 报告渲染、审计和数据质量

### 3.5 Research Packs

每个 Pack 包含：

1. Skill：研究方法、分析顺序、常见误区和输出规范。
2. YAML 配置：实体、产业链、指标、别名、来源、传导关系、阈值和验证周期。
3. 专用代码：仅实现无法通用化的采集和计算。

首批 Pack：

- `pcb`
- `technical-analysis`
- `position-analytics`
- `macro`
- `market-regime`

未来的 `coal` 和 `nonferrous` 复用同一内核，通过新增 Pack 扩展。

### 3.6 pi Agent 层

V1 直接通过 pi 的 TypeScript SDK 嵌入 Agent 能力。pi 负责模型调用、流式生成、工具调用循环、对话上下文、会话持久化、分叉和上下文压缩；项目不包装通用 Runtime，不实现 Adapter，也不复制 pi 已有的 Agent loop。

项目向 pi 注册投研查询和受约束写入工具。工具调用确定性分析层和研究内核，不允许 pi 直接访问或修改 DuckDB 表。写工具必须提供权限检查、幂等键和审计信息，并遵守领域状态机和人工审批规则。

生产投研 session 采用最小权限工具白名单，不加载 pi 默认的 `bash`、`write`、`edit` 和无限制文件读取工具。文件、Shell 和数据库能力必须由项目工具按路径、命令、实体及操作类型约束。开发维护 session 与生产投研 session 分离，开发者明确启动的代码维护任务可以使用 pi 默认编码工具，但不能复用生产聊天的会话、凭据或权限。

V1 使用一个 Research Lead Agent 驱动以下工作流阶段：

- Lead：拆解问题、选择阶段并合并任务状态。
- Industry：研究产业链、供需、技术与竞争格局。
- Company：研究公司暴露、财务与经营变化。
- Technical：解释价格位置、技术状态和相对强弱。
- Macro：解释宏观与市场状态的传导。
- Skeptic：寻找矛盾证据、替代解释和数据缺口。
- Editor：合并结果，检查引用、时效和表达一致性。

这些名称表示可版本化的阶段任务模板，不是独立 Agent。每个模板定义目标、输入、允许读取的数据、结构化输出模式和停止条件；所有阶段共享同一组安全工具白名单，不在会话中动态扩大权限。Research Lead 在一个 pi session 内以普通任务消息依次执行所需阶段。只有实际评测证明上下文隔离或并行执行能显著改善质量时，后续版本才考虑子 session 或子 Agent。

### 3.7 Web Chat Backend

Web Chat Backend 使用 pi SDK 管理研究会话，并通过 SSE 或 WebSocket 向浏览器转发消息增量、工具调用、状态、错误和完成事件。每个 `chat_id` 映射一个 pi session；同一聊天同时只允许一个主动运行，后续消息按“纠正当前运行”或“完成后继续”进入队列。

Chat Backend 负责：

- 创建、恢复、重命名、停止和分叉聊天。
- 将 pi 流式事件转换为 Web 消息、研究轨迹和工具状态。
- 管理模型选择、附件、运行队列、超时和并发限制。
- 将 `chat_id`、pi session、`ResearchRun`、报告和论点变更关联起来。
- 将需要人工确认的写操作暂停为审批请求，收到用户决定后继续。

pi session 保存完整对话和 Agent 过程，但不是投研事实库。事实、指标、证据、论点、催化剂和报告版本仍以研究内核及 DuckDB 为准。删除、分叉或压缩聊天不得删除已经确认的研究资产。

### 3.8 Python 数据服务边界

行情、财务、文档解析和指标计算优先使用 Python 实现；TypeScript Chat Backend 通过窄接口调用 Python 数据服务。Python 数据服务是 DuckDB 和 Parquet 的唯一访问者与唯一写入者，Chat Backend 和 pi 工具不得直接打开数据文件。所有研究查询、运行状态、审批和领域写入都通过 Python 服务完成，从而保持单写者和统一事务边界。

V1 先验证一条垂直链路：pi 调用 Python/DuckDB 查询工具，读取带来源的证据，生成结构化结论并保存 `ResearchRun`。若该边界在部署、类型转换或调试上产生不可接受的复杂度，应在大规模实现前重新比较 Python 原生 Agent 框架。

## 4. 领域数据模型

### 4.1 核心对象

- `Entity`：公司、行业、产品、材料、客户、竞争对手、指数和 ETF。
- `Document`：公告、财报、政策、新闻、纪要和行业资料。
- `Fact`：能够被来源验证的事实陈述。
- `Metric`：包含时间、单位、口径、来源和公式版本的数值。
- `Event`：业绩、扩产、涨价、政策、认证或技术变化等事件。
- `Evidence`：支持或反驳某个研究判断的事实、指标或文档片段。
- `Thesis`：可证伪论点及其状态、证据、置信度、催化剂和失效条件。
- `Catalyst`：未来应验证的时间点或事件。
- `ResearchRun`：一次研究任务的输入、pi 版本、pi session 标识、模型配置、角色配置版本、应用工作流步骤、关键事件、工具调用、输出和错误。
- `ResearchRunStep`：一次可恢复的工作流阶段，记录状态、稳定幂等键、输入摘要、结果引用、pi 消息与工具调用标识、审批状态、错误和时间戳。
- `Snapshot`：某交易日的价格、技术、估值和市场状态快照。
- `ReportVersion`：不可变报告版本及其输入、差异和修订关系。

### 4.2 时间与来源字段

每条事实、指标和证据至少记录：

- 关联实体
- 内容或数值
- 有效时间或报告期
- 对外发布时间
- 来源与原始定位
- 系统获取时间
- 可信等级
- 数据或解析器版本

### 4.3 论点状态机

状态为：

`draft → pending_approval → active → challenged → invalidated → closed`

Agent 可以创建草稿和提出状态变更建议，但以下操作必须由用户确认：

- 激活核心论点
- 将论点标记为失效或关闭
- 改变关键失效条件
- 对受挑战论点恢复有效状态

### 4.4 研究运行与恢复协议

`ResearchRunStep` 状态为：

`pending → running → succeeded | failed | waiting_approval | cancelled`

处于 `waiting_approval` 的步骤在批准后回到 `running`，在拒绝后进入 `cancelled`。`succeeded` 和 `cancelled` 是终态；`failed` 只有在错误被判定可重试时才能回到 `running`。

每个步骤使用由 `run_id + step_name + operation + input_hash` 生成的稳定幂等键。受约束写工具必须先在 Python 数据服务中查询该键：已成功时返回原结果引用，不重复执行；执行中或结果不确定时停止自动重试并要求恢复检查。

步骤开始、工具副作用和步骤完成必须通过 Python 数据服务在可审计的事务边界内记录。无法与外部副作用放入同一数据库事务时，采用“预登记操作 → 执行外部操作 → 保存结果”的协议，并为不确定状态提供人工核对路径。

审批请求是持久化对象，记录请求内容、目标状态、关联步骤、创建时间、决定、决定时间和操作者。进入 `waiting_approval` 后不得预先执行写操作；批准后使用原幂等键继续，拒绝后将步骤终止且不改变领域状态。

恢复运行时以 `ResearchRunStep` 为准，pi session 只用于重建对话上下文。系统从首个未完成步骤继续，不依赖模型自行判断哪些副作用已经执行。

## 5. PCB Research Pack

### 5.1 产业链范围

- 上游：电子纱、电子布、铜箔、树脂及关键材料。
- 中游：覆铜板、高多层 PCB、HDI、相关加工耗材。
- 下游：AI 服务器、交换机和算力基础设施。

### 5.2 公司与产业链映射

- 中国巨石：电子纱、电子布相关上游暴露。
- 生益科技、金安国纪：覆铜板及相关材料。
- 胜宏科技：高端 PCB 制造及 AI 服务器相关需求。
- 中钨高新：PCB 微钻等加工耗材暴露，同时允许关联未来的有色金属 Pack。

### 5.3 首批研究维度

- AI 服务器和交换机资本开支
- PCB 层数、材料等级和产品结构升级
- 产能、产能利用率、良率和客户认证
- 原材料价格与成本传导
- 产品价格、订单、收入和毛利变化
- 竞争格局、扩产节奏和供需错配
- 预期变化如何传导至盈利与估值

## 6. 研究工作流

### 6.1 每日追踪

收盘后执行：

1. 更新行情、基准、宏观和行业数据。
2. 执行交易日、复权、缺失和冲突检查。
3. 计算位置、技术状态、相对强弱、波动和异常。
4. 拉取追踪池公告、新闻和行业变化。
5. 由确定性程序生成变化候选并去重。
6. Agent 判断变化对产业链、公司和既有论点的影响。
7. Skeptic 寻找反方证据、替代解释和缺口。
8. 生成每日变化雷达；重大变化形成待审批的论点修订建议。

没有重大变化时，输出“未发现重大变化”，不生成填充性内容。

### 6.2 每周深度复盘

每周更新：

- 行业与公司核心指标变化
- 公司相对行业和市场的强弱
- 支持与反方证据
- 论点状态和失效条件
- 催化剂兑现、推迟或落空情况
- 市场表现对基本面判断的验证
- 下一周期最需要验证的问题

周报是不可变研究快照，不替代持续更新的行业和公司档案。

### 6.3 即时研究

用户可针对任意行业或公司发起问题。Research Lead 按需执行专业研究阶段，优先复用已有证据，只对缺口发起新检索。

输出必须区分：

- 已确认事实
- 基于事实的推断
- 尚待验证的假设
- 当前无法获得的数据

即时研究对象只有经用户确认后才能加入持续追踪池。

## 7. 周报与版本机制

周报版本采用 `主题-周期-vN` 标识，例如 `PCB-Weekly-2026-W33-v1`。

每个版本记录：

- 数据截止时间和生成时间
- 输入数据源、数据版本和公式版本
- 新增、修改和撤销的事实
- 论点在周期起止时的状态差异
- 新增支持证据和反方证据
- 催化剂状态变化
- Agent 运行记录和人工审批记录
- 与上一版本的结构化差异

已发布版本不可修改。纠错或历史数据修订通过新版本完成，并明确说明改变的数据及其对原判断的影响。活态档案展示最新状态，同时保留完整变更历史。

## 8. 价格、技术与市场状态

### 8.1 多维位置模型

每个标的分别展示：

- 距离 52 周最低价和最高价的幅度
- 52 周区间位置
- 1 年、3 年、5 年价格历史分位
- 均线趋势和偏离程度
- RSI、MACD、KDJ、布林带等透明技术状态
- 成交量、波动率和流动性状态
- 相对行业、指数和竞争对手的强弱
- 个股估值历史分位

ETF 不套用个股估值模型。所有指标显示数据日期、复权方式、公式版本和组件值。

系统输出结构化状态和冲突解释，不将价格低位、技术超卖、估值便宜或基本面见底视为同一概念，也不直接翻译为交易指令。

### 8.2 市场与宏观状态

市场状态面板覆盖：

- 市场宽度、成交额、波动和风险偏好
- 利率、汇率、信用和主要商品价格
- 主要指数、行业轮动和相对强弱
- 宏观变量对经营、估值或二者的影响路径
- 当前环境对既有论点的支持、压制或中性状态

基本面、技术价格和宏观市场三条分析链保持独立，在论点层汇合，不合成为单一股票评分。

## 9. 用户界面与产物

V1 提供本地 Web 工作台和自然语言研究入口，包含：

1. **每日变化雷达**：重要变化、异常程度、影响对象、证据和待研究问题。
2. **PCB 行业驾驶舱**：产业链、趋势指标、公司映射、事件和行业论点。
3. **个股研究档案**：公司暴露、财务变化、证据、价格位置、估值和论点。
4. **价格与位置页面**：K 线、多周期位置、相对强弱、技术状态和计算解释。
5. **论点看板**：按状态管理论点、证据、反证和失效条件。
6. **催化剂与验证日历**：未来验证节点和完成状态。
7. **周报与版本中心**：不可变周报、修订版、差异和证据快照。
8. **Web 研究聊天**：发起即时研究、恢复和分叉会话，并选择性沉淀研究对象。

### 9.1 Web 研究聊天体验

聊天主视图默认只展示用户消息、Agent 回复、来源引用和待审批操作。研究轨迹以可折叠区域展示当前阶段、工具调用、数据日期、耗时和错误，避免底层过程干扰正常阅读。

V1 支持：

- 回复文本流式显示，以及停止和继续研究。
- 新建、恢复、重命名和分叉聊天。
- Agent 运行期间追加纠正消息或排队后续问题。
- 展示工具调用状态、结构化结果摘要和失败原因。
- 上传研究所需的文档或图片，并记录附件来源。
- 展示公告、财报、网页和指标的可点击引用及数据日期。
- 对论点激活、失效条件变更和其他受约束写入进行人工审批。
- 将聊天产物关联到公司档案、证据、论点或报告版本。

Web UI 不直接连接 pi 进程，也不接触模型密钥。浏览器只连接 Chat Backend，由后端管理 pi session、投研工具权限和事件转发。

## 10. 数据可靠性与降级

### 10.1 Provider 记录

每次采集保存来源、请求参数、获取时间、原始响应、适用日期、发布时间、Provider 版本、解析器版本和质量状态。

### 10.2 数据质量检查

- 交易日完整性
- 价格和成交量异常
- 复权因子与公司行动一致性
- 财务单位、币种和报告期一致性
- 多来源冲突
- 文档发布时间与事实时间关系
- 数据新鲜度

### 10.3 降级规则

- 主源失败时切换备用源并记录切换。
- 多来源冲突时保存全部版本并标记冲突。
- 部分指标缺失时输出可完成部分，并说明影响。
- 行情未更新时暂停依赖当日价格的判断，显示上次快照日期。
- pi、模型或研究阶段失败时保留 pi session、`ResearchRun` 和 `ResearchRunStep`；从首个未完成阶段恢复时，已成功的写工具依靠稳定幂等键返回原结果，不重复副作用。
- 无法读取正文时不据此形成事实。
- 证据不足时输出“无法判断”。

每日任务必须幂等。原始数据、标准化数据、派生指标和研究结论分层存储，派生结果可根据输入及公式版本重建。

## 11. 测试策略

### 11.1 单元测试

覆盖复权、价格位置、技术指标、估值分位、相对强弱、时间有效性、单位换算、去重、版本生成、论点状态机和 Pack 配置校验。

### 11.2 Provider 契约测试

所有 Provider 必须输出统一结构。解析器使用固定样本测试，以便外部接口变化时快速失败并报告。

### 11.3 数据质量测试

覆盖缺失交易日、停牌、分红送转、负估值、异常成交量、财务口径变化、重复公告和来源冲突。

### 11.4 Agent 评测

固定案例检查 Agent 是否：

- 区分事实、推断和假设
- 为重要结论提供来源
- 主动寻找反方证据
- 避免自行计算确定性指标
- 遵守状态变更权限
- 在相同证据下保持核心结论稳定

### 11.5 pi 与 Chat Backend 集成测试

使用固定模型响应或受控测试模型覆盖：

- pi 工具注册、参数校验、结果返回和错误传播
- 生产投研 session 不暴露 `bash`、`write`、`edit` 或无限制文件读取工具
- 文本、工具和状态事件向 SSE 或 WebSocket 的转换
- 聊天创建、恢复、停止、分叉和消息排队
- `chat_id`、pi session 与 `ResearchRun` 的关联
- `ResearchRunStep` 状态转换、崩溃窗口恢复和写工具幂等性
- 审批前不执行受约束写入，拒绝后不改变领域状态
- Chat Backend 和 pi 工具无法直接打开 DuckDB 或 Parquet，所有访问都经过 Python 数据服务
- Python 数据服务超时、不可用和返回无效数据时的降级

### 11.6 端到端测试

验证完整链路：

> 变化检测 → 深度研究 → 证据入库 → 论点建议 → 人工确认 → 页面和周报版本

## 12. V1 验收标准

V1 分阶段交付，每个阶段满足退出条件后再扩大范围。

### 12.1 V1a：Agent 垂直链路

- 仅覆盖胜宏科技的一个 PCB 研究问题。
- Web 支持流式问答、停止、历史恢复、工具状态和来源引用。
- pi 只能调用生产投研工具白名单，不能使用默认编码工具。
- 至少一个 Python/DuckDB 查询工具返回带来源和数据日期的结构化结果。
- `chat_id`、pi session、`ResearchRun` 和 `ResearchRunStep` 可追溯关联。
- 崩溃恢复测试证明已成功的受约束写操作不会重复执行。

### 12.2 V1b：持续追踪闭环

- 扩展至五家公司和 PCB Research Pack。
- 实现每日变化雷达、证据沉淀、论点建议和人工审批。
- PCB 核心池连续更新 20 个交易日，不重复事件、不破坏历史快照。
- 数据源失败时能够降级、标记影响范围并恢复。

### 12.3 V1c：复盘与完整工作台

- 实现每周深度复盘、不可变报告版本和结构化差异。
- 完成行业驾驶舱、公司档案、论点看板、催化剂日历和版本中心。
- 支持聊天分叉、附件以及聊天产物向研究资产的受控沉淀。

完整 V1 必须满足：

1. 能解释五家公司当前价格位置及不同维度之间的冲突。
2. 财报发布后能识别关键变化并关联已有论点。
3. 行业材料价格或 AI 服务器需求变化时能展示传导路径。
4. 即时研究陌生公司时不污染持续追踪池。
5. 未经用户确认，Agent 不能激活、反转或关闭核心论点。
6. 关键结论能追溯到原始证据、数据日期和研究过程。
7. 每日追踪、即时研究和周报均通过 pi 的生产投研工具白名单完成，不建设通用 Runtime 或 Adapter。
8. 浏览器无法直接访问 pi 进程、模型密钥、DuckDB、数据文件或未授权工具。

## 13. V1 范围边界

### 13.1 包含

- 本地单用户 Web 工作台
- pi SDK 直接集成与本地 Web 研究聊天
- PCB Research Pack
- 五家公司持续追踪
- 任意 A 股公司的即时研究
- 日线和周线行情本地存储
- 技术位置、估值位置和相对强弱
- 每日变化雷达和版本化每周复盘
- 证据、论点、催化剂和人工审批
- 免费数据源及可替换 Provider 接口

### 13.2 不包含

- 自动交易和组合下单
- 分钟级或 Tick 行情
- 全市场量化选股
- 多用户权限和云端协作
- 移动端应用
- 煤炭、有色的完整 Research Pack
- 复杂组合优化和收益归因
- 付费数据库的正式接入

## 14. 实施约束

第一轮实施应形成一个完整的 PCB 垂直切片，而不是同时铺开所有页面和数据源。建议按以下依赖顺序规划：

> V1a 垂直验证 → V1b 持续追踪闭环 → V1c 复盘与完整工作台

V1a 内部顺序为：生产工具白名单 → Python/DuckDB 单写者服务 → ResearchRun 与步骤状态 → pi 工具调用 → Web 流式聊天 → 引用与恢复测试。首个实现门槛是 Web 发起问题，pi 调用一个带来源的查询工具，流式返回结构化结论，并保存可追溯的研究运行。验证通过后固定 V1 技术选型；验证失败时先重新评估框架，不在已有实现上补建通用 Runtime。

V1 不实现通用 Agent Runtime、框架 Adapter、框架热切换和框架无关的事件协议。Chat Backend 只封装 Web 产品所需的会话、事件转发、权限和业务关联，不承担新的 Agent loop。

旧项目 `ai-stock` 保持不变。新项目可以参考其数据校验、证据存储和测试经验，但不复制其整体架构或历史复杂度。
